# Workflow
- When an audit/verification artifact is verifiable and up-to-date, don't redo or recreate it — leave docs as-is and proceed with execution rather than blocking on re-auditing; only block when verification is genuinely missing or stale. Confidence: 0.9
- When resuming execution after verifying documentation is current, proceed with remaining work in priority order as defined by the planning docs/roadmap rather than arbitrary order. Confidence: 0.7
- Before resuming execution after a corruption/crash incident, explicitly verify there are no null-byte or corrupted files in the source tree — "no null files" is a go/no-go gate the user wants confirmed before proceeding. Confidence: 0.85
- To decide whether an audit/generated artifact is up-to-date, compare its last-write timestamp against the newest source file and check git status for deletions/untracked strays — regenerate only when genuinely stale; a current timestamp is sufficient to leave it as-is. Confidence: 0.6
- When confirming a published package is ready to build on, verify the actual published npm artifact (downloaded tarball/bundle) against the consuming app's real API surface (routes, types, envelope/bare response handling) — not just the repo source or registry metadata. Confidence: 0.85
- Prefer consuming shared packages as external npm dependencies updated via version bumps; upstream in-progress structural changes should not block downstream development. Confidence: 0.8
- Before applying bulk doc updates, show diffs to the user for review first. Confidence: 0.60
- Before a frontend/architecture rebuild, first thoroughly audit both the upstream dependency codebase and the target codebase to build a complete overlap map of what to purge, keep, and refine. Confidence: 0.75
- When auditing a sibling or dependency codebase, produce a categorized analysis covering: what exists (inventory), consumption overlap map, blockers, design inconsistencies, and ranked optimization opportunities for scalability & third-party dynamism — each with actionable recommendations. Confidence: 0.70
- When auditing a codebase that has documented claims (README, AGENTS.md, CLAUDE.md, etc.), explicitly verify each claim against actual codebase reality and produce a "claims vs reality" comparison table — tracking what's been fixed, what's still broken, and what's changed since the doc was written. Confidence: 0.8
- When the user requests an audit of a documented invariant across call sites, cover every path including related ones not explicitly listed (e.g., admin suspend/ban, account deletion, password change), and report which sites are already correct vs. which have gaps — before writing any code. Confidence: 0.7
- When automated exploration/subagent tools fail, fall back to manual systematic exploration (reading files one by one in a structured order) rather than retrying the failed automation. Confidence: 0.75
- After an interrupted session (e.g., IDE crash), trace the repository state — git status/diff/log, session artifacts like `.agent/output.txt`, untracked directories, and lockfile/package.json — to reconstruct what was completed versus what is still open; report this as a structured "what exists / what's still open" summary and ask how the user wants to proceed rather than acting unilaterally. Confidence: 0.85
- When tracing an interrupted session, verify that plan/session artifacts (e.g., files in a shared `~/.commandcode/plans` dir) actually belong to the current repo before treating them as in-flight work — cross-project contamination is common when one machine hosts multiple projects. Confidence: 0.70
- When shell commands fail to resolve paths that clearly exist (e.g., Windows CRLF/encoding path issues), fall back to the dedicated directory/file reading tools instead of retrying the failing shell command. Confidence: 0.60
- When running into a full-tree scan that hangs/times out (e.g., on node_modules), scope the scan to relevant directories (src, prisma, docs, scripts, root) instead of retrying the full recursive scan. Confidence: 0.6
- When verification reveals small untracked stray artifacts (empty dirs from mis-typed flags, truncated/aborted output stubs like a 2-byte `^C` file), remove them and regenerate the affected snapshot/audit so the tree and its artifacts stay in sync. Confidence: 0.6
- The user asks for the assistant's opinion ("what'd you think") before committing to large/destructive changes such as deleting dependencies — respond with an evidence-based recommendation and a safe execution order rather than immediately executing. Confidence: 0.7
- Before building anything new, first verify what already exists in the installed packages/dependencies (their actual exported API surface) to avoid recreating what's already built — don't conclude something needs to be written until the existing package's capabilities are confirmed. Confidence: 0.85
- For large multi-part implementation (e.g., wiring pages end-to-end), decide the architecture explicitly up front, then execute in verifiable phases — not one-shot big-bang. The user stated this outright: "architecturally decide the design and also execute in phases." Confidence: 0.8
- Likes to run independent workstreams in parallel (e.g., building arc-wallet concurrently with page-wiring phases) rather than strictly serializing them — explicitly invited parallel work in a sibling repo directory (../arc-wallet) alongside the main repo. Confidence: 0.75
- When a downstream consumer could alternatively wait for prod, the user wants an explicit build-now-vs-wait decision backed by verification of the integration seam (worst case = base-URL/param change, not a rewire; only runtime concerns like CORS/TLS/rate-limits gate on prod) — resolve that risk before starting, don't assume. Confidence: 0.6
